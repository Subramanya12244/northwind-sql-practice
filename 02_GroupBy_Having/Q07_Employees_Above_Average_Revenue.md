# Q07 · Employees Above Average Revenue

> **Revision Card**
> **Category:** GROUP BY & HAVING | **Difficulty:** Medium
> **Concepts:** INNER JOIN · GROUP BY · CTE · SUM/AVG · Scalar Subquery
> **Outcome:** ✅ correct first attempt
> **Watch out for:** group by `employee_id` (not name) so two employees sharing a name aren't silently merged.

## 1. Problem

Sales management wants to identify which employees are performing above the team's average revenue contribution, to recognize strong performers.

**Objective:** Return all employees whose total revenue exceeds the average total revenue computed across all employees.

**Tables:** `employees`, `orders`, `order_details`

**Expected output:**

| Column | Description |
|---|---|
| employee_id | Unique identifier of the employee |
| first_name | Employee's first name |
| last_name | Employee's last name |
| total_revenue | Sum of discounted revenue generated by this employee |

| employee_id | first_name | last_name | total_revenue |
|---|---|---|---|
| 4 | Margaret | Peacock | 232890.85 |
| 3 | Janet | Leverling | 202812.84 |
| 1 | Nancy | Davolio | 192107.60 |
| 2 | Andrew | Fuller | 166537.76 |

*(Sample values are illustrative, based on the standard Northwind dataset — not guaranteed to match your exact data instance.)*

## 2. My Approach

1. Build a CTE (`employee_revenue`) that calculates each employee's total discounted revenue.
2. Select from that CTE in the outer query.
3. Filter using a scalar subquery computing `AVG(total_revenue)` over the whole CTE.
4. Sort by total revenue descending.

## 3. My Solution (as submitted)

```sql
WITH employee_revenue AS (
    SELECT
        e.employee_id,
        e.first_name,
        e.last_name,
        SUM(od.unit_price * od.quantity * (1 - od.discount)) AS total_revenue
    FROM employees e
    JOIN orders o ON o.employee_id = e.employee_id
    JOIN order_details od ON od.order_id = o.order_id
    GROUP BY e.employee_id, e.first_name, e.last_name
)
SELECT *
FROM employee_revenue
WHERE total_revenue > (SELECT AVG(total_revenue) FROM employee_revenue)
ORDER BY total_revenue DESC;
```

## 6. Why This Works

**Why the same CTE-then-compare pattern as Q6:** the underlying problem structure is identical — 'above the average across the group' always requires computing per-entity totals first, then comparing each to an independently computed average over the full set.

## 7. Common Pitfalls (generic)

- Same as Q6 — attempting `HAVING SUM(x) > AVG(x)` directly instead of via an independently computed average.
- Grouping by name only instead of `employee_id`, risking incorrect merges if two employees share a name.

## 8. Interview Follow-ups

**1. How is this query structurally identical to Q6, just applied to a different entity?**

Both use the identical "CTE of per-entity totals, then filter against a scalar subquery averaging that CTE" pattern. The only differences are the base table and join key: Q6 groups `customers` by `customer_id` joining `orders.customer_id`, while Q7 groups `employees` by `employee_id` joining `orders.employee_id`. The revenue expression `SUM(od.unit_price * od.quantity * (1 - od.discount))`, the `WHERE total_revenue > (SELECT AVG(total_revenue) ...)` comparison, and the `ORDER BY ... DESC` are unchanged.

**2. How would you generalize this into a reusable view or function if this 'above average revenue' check needed to be run for customers, employees, AND shippers?**

Create one view per entity (e.g. `employee_revenue`, `customer_revenue`) exposing a uniform `(entity_id, name, total_revenue)` shape, then write a single generic query or a parameterized SQL/PLpgSQL function that takes the view/table name and applies the same `total_revenue > (SELECT AVG(total_revenue) ...)` filter — using dynamic SQL (`EXECUTE format(...)`) when the source must be a parameter. Alternatively, a set-returning function `above_average(revenue_set)` could accept the pre-aggregated set so the averaging logic lives in exactly one place.

**3. What would change if 'average' should mean median instead of mean?**

Replace the `AVG(total_revenue)` scalar subquery with PostgreSQL's ordered-set aggregate `PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY total_revenue)` over the same CTE. The median is robust to outliers (a few very high performers won't pull the threshold up the way `AVG` does), so more employees may qualify as "above the typical performer." The surrounding CTE-then-compare structure stays the same.

## 9. Key Takeaway

Recognize and reuse the 'CTE + scalar subquery average comparison' pattern across different entities (customers, employees) — the same structure transfers directly, only the base table and key change.
