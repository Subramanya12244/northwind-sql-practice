# Q06 · Customers Above Average Revenue

> **Revision Card**
> **Category:** GROUP BY & HAVING | **Difficulty:** Medium
> **Concepts:** INNER JOIN · GROUP BY · CTE · SUM/AVG · Scalar Subquery
> **Outcome:** ✅ correct first attempt
> **Watch out for:** you can't write `HAVING SUM(revenue) > AVG(revenue)` — the average must be computed independently across *all* customer totals, not within one group.

## 1. Problem

Finance wants to flag customers whose lifetime revenue exceeds the average revenue across all customers, to separate above-average accounts from the long tail for targeted upsell campaigns.

**Objective:** Return all customers whose total revenue is strictly greater than the average total revenue computed across all customers.

**Tables:** `customers`, `orders`, `order_details`

**Expected output:**

| Column | Description |
|---|---|
| customer_id | Unique identifier of the customer |
| company_name | Name of the customer's company |
| total_revenue | Sum of discounted revenue generated by this customer |

| customer_id | company_name | total_revenue |
|---|---|---|
| QUICK | QUICK-Stop | 117483.39 |
| ERNSH | Ernst Handel | 104874.98 |
| SAVEA | Save-a-lot Markets | 104361.95 |
| RATTC | Rattlesnake Canyon Grocery | 51097.80 |
| HUNGO | Hungry Owl All-Night Grocers | 49979.91 |

*(Sample values are illustrative, based on the standard Northwind dataset — not guaranteed to match your exact data instance.)*

## 2. My Approach

1. Build a CTE (`customer_revenue`) that calculates each customer's total discounted revenue.
2. In the outer query, select from that CTE.
3. Filter using a scalar subquery that computes `AVG(total_revenue)` across the entire CTE.
4. Sort by total revenue descending.

## 3. My Solution (as submitted)

```sql
WITH customer_revenue AS (
    SELECT
        cu.customer_id,
        cu.company_name,
        SUM(od.unit_price * od.quantity * (1 - od.discount)) AS total_revenue
    FROM customers cu
    JOIN orders o ON o.customer_id = cu.customer_id
    JOIN order_details od ON od.order_id = o.order_id
    GROUP BY cu.customer_id, cu.company_name
)
SELECT *
FROM customer_revenue
WHERE total_revenue > (SELECT AVG(total_revenue) FROM customer_revenue)
ORDER BY total_revenue DESC;
```

## 6. Why This Works

**Why a CTE is needed instead of plugging straight into `HAVING`:** `HAVING SUM(revenue) > AVG(SUM(revenue))` looks intuitive but doesn't work — `AVG()` over `SUM()` would just average the *current group's* single revenue value (itself), not the average across *all* customer groups. The average must be computed independently, across the full set of per-customer totals, which requires materializing those totals first (via a CTE or subquery) before comparing.

**Why the CTE is referenced twice:** once to list the rows, and once inside a scalar subquery to compute `AVG(total_revenue)` over the *entire* CTE result set — independent of any single customer's row.

## 7. Common Pitfalls (generic)

- Writing `HAVING SUM(revenue) > AVG(revenue)` directly, expecting it to compare against the global average — it doesn't; `AVG()` here would just equal `SUM()` for a single group of one value.
- Forgetting to recompute revenue identically in both halves (the CTE and the comparison) which can introduce subtle mismatches in more complex variants.
- Treating 'average customer revenue' as 'average order revenue' — these are very different denominators (one is per-customer, the other is per-order).

## 8. Interview Follow-ups

**1. Why can't you just write `HAVING SUM(revenue) > AVG(revenue)` to solve this in one pass?**

`HAVING` filters each group after aggregation, so within a single customer's group the only value available to `AVG()` is that one customer's own `SUM(revenue)` — averaging one value just returns it, making the comparison `x > x` (always false). The global average must be computed across *all* per-customer totals, which don't exist until every group has been aggregated. That requires materializing the per-customer totals first (the `customer_revenue` CTE) and then averaging over that full set in a separate scalar subquery.

**2. What's the difference between this CTE-based approach and a correlated subquery approach (see Q16) for the same problem?**

The CTE here computes every customer's total once and the scalar subquery averages that materialized set a single time — the average is evaluated once for the whole query. A correlated subquery instead re-executes the inner aggregation for each outer row, which is both harder to read and typically slower because the per-customer revenue work can be repeated. For an "above the global average" check the CTE pattern is cleaner; correlated subqueries fit better when the comparison depends on the current row (e.g. "above the average for *this customer's* country").

**3. How would the result change if you used `AVG(revenue)` computed from `order_details` directly, rather than from per-customer aggregated totals?**

`AVG(unit_price * quantity * (1 - discount))` over raw `order_details` rows produces the average revenue *per line item*, a much smaller number than the average *per customer* (each customer has many lines). Comparing per-customer totals against a per-line-item average would mark almost every customer as "above average," answering a completely different question. The denominator must be the number of customers, not the number of order-detail rows.

**4. How would you find customers within, say, 10% of the average rather than strictly above it?**

Replace the strict `>` with a `BETWEEN` band around the average computed from the same CTE: `WHERE total_revenue BETWEEN 0.9 * (SELECT AVG(total_revenue) FROM customer_revenue) AND 1.1 * (SELECT AVG(total_revenue) FROM customer_revenue)`. To avoid repeating the scalar subquery, you can compute the average once in a second CTE (or `CROSS JOIN` it) and reference the lower and upper bounds from there.

## 9. Key Takeaway

'Above average' comparisons require two passes: aggregate per entity first, then aggregate across entities. The CTE pattern materializes that intermediate set so it can be both displayed and used in the comparison.
