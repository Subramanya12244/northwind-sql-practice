# Q18 · Customer Revenue Above Employee Average

> **Revision Card**
> **Category:** Correlated Subqueries | **Difficulty:** Hard
> **Concepts:** CTE · Correlated Subquery · GROUP BY · Aggregates (SUM, AVG)
> **Outcome:** ✅ correct first attempt
> **Watch out for:** the correlation condition (`ecr2.employee_id = ecr.employee_id`) is what makes the average per-employee — drop it and it collapses to a single global average.

## 1. Problem

Sales management wants, for every employee, to identify which of *their* customers generate above-average revenue *relative to that employee's own customer base* — not relative to the company as a whole. This supports per-employee account prioritization.

**Objective:** For each employee, return the customers whose revenue (from orders handled by that employee) exceeds the average revenue of all customers handled by that same employee.

**Tables:** `orders`, `order_details`

**Expected output:**

| Column Name | Description |
|-------------|-------------|
| employee_id | Employee who handled the orders |
| customer_id | Customer whose revenue is being evaluated |
| revenue | Revenue generated by this customer, specifically from orders handled by this employee |

| employee_id | customer_id | revenue |
|-------------|-------------|---------|
| 4 | QUICK | 28734.90 |
| 4 | SAVEA | 21345.10 |
| 3 | ERNSH | 19872.55 |
| 1 | HUNGO | 15234.40 |

*(Sample values are illustrative, based on the standard Northwind dataset, and intended to show shape/format — not guaranteed to match your exact data instance.)*

## 2. My Approach

1. Build a CTE (`employee_customer_revenue`) that aggregates revenue per employee-customer pair.
2. In the outer query, select from that CTE.
3. Filter using a correlated subquery that computes `AVG(revenue)` for *only the rows matching the current row's `employee_id`*.
4. Sort by employee and then by revenue descending.

## 3. My Solution (as submitted)

```sql
WITH employee_customer_revenue AS (
    SELECT
        o.employee_id,
        o.customer_id,
        SUM(od.unit_price * od.quantity * (1 - od.discount)) AS revenue
    FROM orders o
    JOIN order_details od ON od.order_id = o.order_id
    GROUP BY o.employee_id, o.customer_id
)
SELECT
    ecr.employee_id,
    ecr.customer_id,
    ROUND(ecr.revenue::numeric, 2) AS revenue
FROM employee_customer_revenue ecr
WHERE ecr.revenue > (
    SELECT AVG(ecr2.revenue)
    FROM employee_customer_revenue ecr2
    WHERE ecr2.employee_id = ecr.employee_id   -- correlation
)
ORDER BY ecr.employee_id, ecr.revenue DESC;
```

## 6. Why This Works

**Why this is a genuinely correlated subquery, unlike Q15-Q17:** the inner subquery's `WHERE ecr2.employee_id = ecr.employee_id` clause directly references `ecr.employee_id` — a column from the *outer* query's current row. This means the inner query cannot be evaluated once and reused; it must be logically re-evaluated for every distinct employee in the outer result, computing that specific employee's own customer-average each time.

**Why the average is 'per employee', not global:** this is precisely what distinguishes this question from Q6/Q16 — those compare a customer to the *company-wide* average; this compares a customer to the average *within the specific employee's portfolio*. The grain of comparison is fundamentally narrower.

**Why a CTE is used to pre-aggregate `employee_customer_revenue` before applying the correlated filter:** without it, the correlated subquery would need to repeat the full `orders`/`order_details` join and revenue calculation inside the subquery itself, on every outer row — far more verbose and considerably more expensive to execute.

## 7. Common Pitfalls (generic)

- Comparing against the company-wide average instead of the per-employee average — this collapses the correlation entirely and turns the query into a variant of Q16.
- Forgetting the correlation condition (`ecr2.employee_id = ecr.employee_id`) in the inner subquery, which would make it non-correlated and compute a single global average instead of one per employee.
- Not pre-aggregating revenue in a CTE first, leading to a much more expensive and harder-to-read query that recomputes joins inside the correlated subquery.

## 8. Interview Follow-ups

**1. What makes this subquery correlated, specifically? Point to the exact clause.**

The clause `WHERE ecr2.employee_id = ecr.employee_id` is what makes it correlated — `ecr.employee_id` is a column from the outer query's current row, referenced inside the inner query. Because the inner query depends on that outer value, it cannot be evaluated once and cached; it must be logically re-evaluated for each distinct employee, computing that employee's own customer-revenue average each time. Remove that clause and the subquery becomes non-correlated, collapsing to a single global average.

**2. How does the average computed in this query differ conceptually from the average computed in Q6?**

Q6 compares each customer against the *company-wide* average revenue across all customers — one global benchmark for everyone. This query compares each customer against the average only within a single employee's own portfolio, so the benchmark is different for every employee. The grain of comparison is narrower: a customer could be above average for one employee's book of business but below the company-wide figure, and vice versa.

**3. Why does pre-aggregating into a CTE before applying the correlated filter help performance, even though the subquery is still technically correlated?**

The CTE `employee_customer_revenue` computes the expensive `orders`/`order_details` join and revenue sum once, producing a compact set of employee-customer rows. The correlated subquery then re-scans that small pre-aggregated set per outer row instead of re-running the full join and aggregation each time. So the correlation cost is paid against a tiny intermediate result rather than the raw detail tables, which is far cheaper and much more readable.

**4. How would you rewrite this using a window function (e.g. `AVG(...) OVER (PARTITION BY employee_id)`) instead of a correlated subquery? What would change?**

Add `AVG(revenue) OVER (PARTITION BY employee_id)` as a column computed over the pre-aggregated CTE, then filter in an outer query where `revenue > that windowed average`. For example: `SELECT * FROM (SELECT employee_id, customer_id, revenue, AVG(revenue) OVER (PARTITION BY employee_id) AS emp_avg FROM employee_customer_revenue) t WHERE revenue > emp_avg`. This computes each employee's average in a single pass rather than re-executing a subquery per row, so it is typically faster and arguably clearer; you need the extra outer wrapper because window functions cannot be used directly in `WHERE`.

**5. If an employee has only one customer, would that customer ever appear in this result? Why or why not?**

No. With a single customer, that customer's revenue *is* the employee's average, so the strict comparison `revenue > AVG(revenue)` is never satisfied (a value cannot be greater than itself). The customer would only qualify under a `>=` comparison. This is the general behavior at the boundary: strictly-above-average filters always exclude the sole or tied-maximum member of a group.

## 9. Key Takeaway

A correlated subquery references an outer-row column and re-evaluates per row — here it yields a per-employee average; pre-aggregate into a CTE first to keep it cheap and readable.
