# Q22 · Top Employee by Revenue Using 3 CTEs

> **Revision Card**
> **Category:** Common Table Expressions (CTEs) | **Difficulty:** Medium
> **Concepts:** CTE (chained) · GROUP BY · SUM/MAX · Tie Handling · INNER JOIN
> **Outcome:** ✅ correct first attempt
> **Watch out for:** `ORDER BY ... LIMIT 1` silently drops ties — compare to `MAX()` so every tied top employee is returned.

## 1. Problem

Leadership wants to identify the single highest-revenue employee company-wide, with the requirement that ties be handled correctly — if two employees are exactly tied for first, both should be returned, not an arbitrary one.

**Objective:** Find the employee(s) with the single highest total revenue, using a layered three-CTE structure: aggregate, find the maximum, then filter to matches.

**Tables:** `employees`, `orders`, `order_details`

**Expected output:**

| Column Name | Description |
|-------------|-------------|
| employee_id | Unique identifier of the top-revenue employee |
| first_name | Employee's first name |
| last_name | Employee's last name |
| total_revenue | Total discounted revenue generated by this employee (the company-wide maximum) |

| employee_id | first_name | last_name | total_revenue |
|-------------|------------|-----------|---------------|
| 4 | Margaret | Peacock | 232890.85 |

*(Sample values are illustrative, based on the standard Northwind dataset, and intended to show shape/format — not guaranteed to match your exact data instance.)*

## 2. My Approach

1. Build a CTE (`employee_revenue`) aggregating discounted revenue per employee.
2. Build a second CTE (`max_revenue`) computing the single highest revenue value across all employees.
3. Build a third CTE (`ranked_employees`) joining the first two on equality (`total_revenue = max_rev`), which naturally includes every tied employee.
4. Select and round the final result from `ranked_employees`.

## 3. My Solution (as submitted)

```sql
WITH employee_revenue AS (
    SELECT
        e.employee_id,
        e.first_name,
        e.last_name,
        SUM(od.unit_price * od.quantity * (1 - od.discount)) AS total_revenue
    FROM employees e
    JOIN orders o ON o.employee_id = e.employee_id
    JOIN order_details od ON od.order_id = o.order_id
    GROUP BY e.employee_id, e.first_name, e.last_name
),
max_revenue AS (
    SELECT MAX(total_revenue) AS max_rev
    FROM employee_revenue
),
ranked_employees AS (
    SELECT er.*
    FROM employee_revenue er
    JOIN max_revenue mr ON er.total_revenue = mr.max_rev
)
SELECT
    employee_id,
    first_name,
    last_name,
    ROUND(total_revenue::numeric, 2) AS total_revenue
FROM ranked_employees;
```

## 6. Why This Works

**Why three CTEs instead of a simple `ORDER BY ... LIMIT 1`:** `LIMIT 1` would silently return just one row even if two employees are exactly tied for the highest revenue — failing the explicit 'handle ties correctly' requirement. Comparing directly against `MAX(total_revenue)` instead naturally returns *every* employee whose revenue equals that maximum, ties included, with no extra logic required.

**Why chain three CTEs rather than two:** `employee_revenue` aggregates revenue per employee; `max_revenue` reduces that to a single scalar (the company-wide highest); `ranked_employees` joins the two together on equality, naturally catching every tie. Each CTE has a single, clear responsibility, which makes the query easy to read top-to-bottom and easy to debug by inspecting any one CTE in isolation.

## 7. Common Pitfalls (generic)

- Using `ORDER BY total_revenue DESC LIMIT 1`, which breaks the explicit tie-handling requirement by returning only one row even when multiple employees are tied.
- Using `RANK() = 1` instead of comparing to `MAX()` directly — both work correctly here, but `MAX()`-based equality is arguably simpler when you only care about the single top group, not a full ranking.

## 8. Interview Follow-ups

**1. Why is `LIMIT 1` the wrong tool here, given the tie-handling requirement?**

`ORDER BY total_revenue DESC LIMIT 1` returns exactly one row regardless of ties, so if two employees had identical top revenue it would arbitrarily keep one and silently drop the other — violating the explicit requirement that both tied employees be returned. Comparing against `MAX(total_revenue)` with equality instead returns every employee whose revenue equals the maximum, so all tied top performers surface automatically.

**2. Walk through what each of the three CTEs is responsible for, and why splitting them this way aids readability.**

`employee_revenue` aggregates discounted revenue per employee (the detail layer). `max_revenue` reduces that detail to a single scalar — the company-wide highest revenue. `ranked_employees` joins the detail back to that scalar on equality (`total_revenue = max_rev`), keeping only the employee(s) at the maximum. Each CTE has one responsibility — aggregate, reduce, filter — so the query reads top-to-bottom as a pipeline and any layer can be inspected in isolation when debugging.

**3. How would you adapt this to find the top employee per *region* rather than company-wide?**

Switch from the scalar-MAX approach to a partitioned window function, since the "maximum" is now per group. Carry `region` through `employee_revenue`, then apply `RANK() OVER (PARTITION BY region ORDER BY total_revenue DESC)` and filter `rnk = 1`. That returns each region's top employee(s), ties included — the same partitioned-ranking pattern used in Q23 and Q24.

**4. Could this be solved with `RANK()` instead of comparing to `MAX()`? What would change?**

Yes — `RANK() OVER (ORDER BY total_revenue DESC)` with a filter of `rnk = 1` is equivalent and also preserves ties (all tied top employees get rank 1). What changes is the mechanism: `RANK()` computes the ordering in a single windowed pass rather than requiring a separate MAX scalar and an equality join. `RANK()` scales more naturally if the requirement later grows to "top N," whereas the `MAX()` equality is arguably simpler when you only ever need the single top group.

## 9. Key Takeaway

For 'top 1 with ties', compare against `MAX()` (not `LIMIT 1`) so every tied row surfaces; chain CTEs each with one clear responsibility — aggregate, reduce, filter.
