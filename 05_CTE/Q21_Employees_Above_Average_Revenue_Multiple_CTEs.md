# Q21 · Employees Above Average Revenue Using Multiple CTEs

> **Revision Card**
> **Category:** Common Table Expressions (CTEs) | **Difficulty:** Medium
> **Concepts:** CTE (multiple) · INNER JOIN (non-equality condition) · GROUP BY · SUM/AVG
> **Outcome:** ✅ correct first attempt
> **Watch out for:** `JOIN ... ON >` is only safe because the average CTE is single-row — against a multi-row CTE it becomes a non-equi join that explodes result rows.

## 1. Problem

Restating Q7's business need using a two-CTE structure (employee revenue, then average revenue), joined together with an explicit `JOIN ... ON` condition that doubles as the filter.

**Objective:** Calculate employee revenue in one CTE, average revenue in a second CTE, and join them using the comparison itself as the join condition.

**Tables:** `employees`, `orders`, `order_details`

**Expected output:**

| Column Name | Description |
|-------------|-------------|
| employee_id | Unique identifier of the employee |
| first_name | Employee's first name |
| last_name | Employee's last name |
| total_revenue | Sum of discounted revenue generated by this employee |

| employee_id | first_name | last_name | total_revenue |
|-------------|------------|-----------|---------------|
| 4 | Margaret | Peacock | 232890.85 |
| 3 | Janet | Leverling | 202812.84 |
| 1 | Nancy | Davolio | 192107.60 |

*(Sample values are illustrative, based on the standard Northwind dataset, and intended to show shape/format — not guaranteed to match your exact data instance.)*

## 2. My Approach

1. Build a CTE (`employee_revenue`) for per-employee discounted revenue.
2. Build a second CTE (`avg_revenue`) producing the single average revenue value across all employees.
3. Join the two CTEs using `ON er.total_revenue > ar.avg_rev` as the join condition itself.
4. Sort by total revenue descending.

## 3. My Solution (as submitted)

```sql
WITH employee_revenue AS (
    SELECT
        e.employee_id,
        e.first_name,
        e.last_name,
        SUM(od.unit_price * od.quantity * (1 - od.discount)) AS total_revenue
    FROM employees e
    JOIN orders o ON o.employee_id = e.employee_id
    JOIN order_details od ON od.order_id = o.order_id
    GROUP BY e.employee_id, e.first_name, e.last_name
),
avg_revenue AS (
    SELECT AVG(total_revenue) AS avg_rev
    FROM employee_revenue
)
SELECT er.*
FROM employee_revenue er
JOIN avg_revenue ar ON er.total_revenue > ar.avg_rev
ORDER BY er.total_revenue DESC;
```

## 6. Why This Works

**Why `JOIN avg_revenue ar ON er.total_revenue > ar.avg_rev` is valid and useful:** SQL `JOIN ... ON` conditions aren't restricted to equality — any boolean expression is valid. Since `avg_revenue` produces exactly one row, this join condition effectively performs the filter directly within the join step rather than via a separate `WHERE` clause — functionally identical to Q19's `WHERE` version, but demonstrating that joins can encode inequality comparisons, not just equality lookups.

**Why this only works safely because `avg_revenue` is single-row:** if it returned multiple rows, this `JOIN ... ON >` condition would behave like a non-equi join, potentially producing a cross-product-like explosion of rows where each employee row is matched against every qualifying average row.

## 7. Common Pitfalls (generic)

- Using this same `JOIN ... ON >` pattern against a multi-row CTE, not realizing it could create unwanted row multiplication.
- Assuming `JOIN` conditions must always be equality — a common but incorrect assumption for SQL beginners.

## 8. Interview Follow-ups

**1. Is `JOIN ... ON >` valid SQL? What would happen if the right-hand CTE returned more than one row?**

Yes — a `JOIN ... ON` condition accepts any boolean expression, not just equality, so `ON er.total_revenue > ar.avg_rev` is valid. It works cleanly here only because `avg_revenue` is a single-row scalar: each employee is compared once against the one benchmark and kept if above it. If the right side returned multiple rows, the inequality would behave like a non-equi join, matching each employee against every average row that satisfies the comparison and multiplying the result set — an employee above two of three averages would appear twice.

**2. How is this functionally different from filtering with `WHERE` after a `JOIN ... ON true` or cross join?**

Functionally it is identical. Putting the predicate in the `ON` clause of an inner join versus cross-joining and putting the same predicate in `WHERE` produces the same rows, because for an INNER join the planner applies `ON` and `WHERE` conditions equivalently. The difference is only expressive: the `ON >` version encodes the filter as part of the join step, while the cross-join-plus-`WHERE` version separates combining from filtering. (The equivalence breaks only for OUTER joins, where `ON` and `WHERE` behave differently.)

**3. Would you recommend this pattern in production code, or is `WHERE` clearer? Justify your answer.**

For production I would prefer the `WHERE` form (as in Q19). An inequality in a join `ON` clause reads as a join relationship, which misleads a reader into thinking there is a real key linking the tables, when the intent is actually "filter against a benchmark." The `WHERE` version states that intent plainly and is less likely to be copied into a multi-row context where it would silently explode rows. The `ON >` pattern is a useful teaching device but a readability trap in shared code.

## 9. Key Takeaway

`JOIN ... ON` accepts arbitrary boolean conditions, not just equality — useful for 'compare to benchmark' queries, but only safe when the right-hand side's cardinality (here, one row) is guaranteed.
